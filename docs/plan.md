# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 BuildLog 기능을 React 프론트엔드, FastAPI 백엔드, Supabase 실제 서비스 데이터베이스로 만드는 순서를 설명합니다.

자동 테스트는 실제 서비스 데이터에 영향을 주지 않도록 SQLite3를 사용합니다. 한 번에 하나의 Phase만 진행하고, 각 Phase의 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 확정한 기술 구조

| 구분 | 사용 기술 | 역할 |
| --- | --- | --- |
| 프론트엔드 | React, HTML, CSS, JavaScript | 사용자가 보는 화면과 사용자 입력 처리 |
| 백엔드 | Python, FastAPI | 로그인, 권한, 기록 관리와 API 제공 |
| 실제 서비스 DB | Supabase PostgreSQL | 온라인 서비스의 실제 사용자 데이터 저장 |
| 자동 테스트 DB | SQLite3 | 외부 서비스 없이 빠르고 독립적인 테스트 실행 |

정확한 버전과 데이터베이스 연결 도구는 Phase 0에서 호환되는 안정 버전으로 결정합니다. PostgreSQL과 SQLite3에서 같은 기능이 동작하도록 특정 데이터베이스에만 있는 기능에는 의존하지 않습니다.

## 3. 개발 원칙

- `spec.md`에 없는 사용자 기능은 추가하지 않습니다.
- 프론트엔드와 백엔드는 API로 통신합니다.
- 화면에서 버튼을 숨기는 것과 별개로 FastAPI에서도 로그인·소유자·운영자 권한을 검사합니다.
- 비밀번호는 안전하게 변환해서 저장하고 원문을 보관하지 않습니다.
- 비밀 설정은 `.env`에만 두고 `.env.example`에는 항목 이름과 비밀이 아닌 예시만 기록합니다.
- 실제 Supabase 데이터는 자동 테스트에 사용하지 않습니다.
- 테스트는 매번 새로운 SQLite3 데이터베이스에서 독립적으로 실행할 수 있어야 합니다.
- 데이터 구조 변경은 마이그레이션으로 관리하며 Supabase와 SQLite3 양쪽에서 확인합니다.
- 각 Phase가 끝나면 백엔드 자동 테스트와 프론트엔드 동작 확인을 함께 수행합니다.
- Git 초기화와 커밋은 별도 요청 전까지 수행하지 않습니다.

## 4. 예정된 프로젝트 구조

```text
buildlog/
├─ backend/
│  ├─ app/
│  │  ├─ api/          # FastAPI 주소와 요청 처리
│  │  ├─ core/         # 환경 설정, 인증, 공통 기능
│  │  ├─ db/           # DB 연결과 마이그레이션 설정
│  │  ├─ models/       # 데이터 구조
│  │  ├─ schemas/      # API 입력·출력 규칙
│  │  └─ services/     # 기록, 검색, 권한 처리
│  ├─ migrations/      # 데이터 구조 변경 내역
│  ├─ tests/           # SQLite3를 사용하는 자동 테스트
│  ├─ requirements.txt
│  └─ .env.example
├─ frontend/
│  ├─ src/
│  │  ├─ api/          # FastAPI 호출 코드
│  │  ├─ components/   # 공통 버튼, 입력, 카드, 안내
│  │  ├─ pages/        # 기능별 화면
│  │  ├─ styles/       # 공통·반응형 CSS
│  │  └─ App.jsx       # 화면 이동 시작점
│  ├─ package.json
│  └─ .env.example
├─ database/
│  └─ README.md        # Supabase·SQLite3 사용 방법과 주의사항
└─ docs/
```

세부 파일 이름은 사용하는 라이브러리의 표준 구조에 따라 조금 달라질 수 있지만, `frontend`, `backend`, `database`, `docs`의 역할은 유지합니다.

## 6. Phase별 상세 계획

### Phase 0. 기술 버전과 실행 환경 확인

**상태: 완료 (2026-10-26)**

확정된 버전, 개발 주소, 도구와 환경 변수는 `docs/setup.md`에 기록했습니다. 이 Phase에서는 패키지 설치와 애플리케이션 코드 생성을 수행하지 않았습니다.

#### 목표

패키지를 설치하거나 코드를 만들기 전에 현재 컴퓨터와 문서 기준을 확인하고, 사용할 도구와 환경 변수 이름을 확정합니다.

#### 작업

1. `mvp.md`, `PRD.md`, `spec.md`, `plan.md`의 기능과 기술 구성이 일치하는지 확인합니다.
2. 첫 버전에서 만들지 않는 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 설치된 Python, Node.js, npm 실행 여부와 버전을 읽기 전용으로 확인합니다.
4. FastAPI와 호환되는 안정 Python 버전을 정합니다.
5. React 개발 환경과 호환되는 안정 Node.js 버전을 정합니다.
6. FastAPI, 데이터 검증, ORM, 마이그레이션, 비밀번호 처리, 테스트 도구의 조합을 정합니다.
7. React 프로젝트 생성·실행 도구와 프론트엔드 테스트 도구를 정합니다.
8. 개발 주소를 정합니다.
   - 프론트엔드 개발 서버 주소
   - FastAPI 개발 서버 주소
   - API 기본 경로
9. 프론트엔드와 백엔드가 서로 요청할 수 있도록 허용할 개발 주소를 정합니다.
10. 환경 변수 이름을 정리합니다.
    - 실제 서비스 DB 연결 주소
    - 테스트 DB 주소
    - 인증 비밀값
    - 프론트엔드의 API 주소
11. Supabase 프로젝트가 준비되었는지 확인하되, 비밀 연결값을 출력하거나 문서에 기록하지 않습니다.
12. Phase 1부터 사용할 설치·실행·테스트 명령을 정리합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요하면 `docs/setup.md`의 초기 틀
- 이 Phase에서는 애플리케이션 코드와 패키지를 변경하지 않음

#### 확인 방법

- 네 문서에 이전 기술 구조나 실제 서비스 DB를 SQLite3로 사용한다는 설명이 남아 있지 않은지 확인합니다.
- Python, Node.js, npm을 실행할 수 있는지 확인합니다.
- 선택한 도구가 Supabase PostgreSQL과 SQLite3를 모두 지원하는지 확인합니다.
- 필요한 환경 변수의 이름과 용도를 설명할 수 있는지 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 변경하지 않았는지 확인합니다.

#### 완료 조건

- 버전, 도구, 개발 주소, 환경 변수 이름이 확정되어 있습니다.
- 사용자에게 받아야 할 비밀값과 필요한 시점이 분명합니다.
- Phase 1을 막는 환경 문제가 없습니다.

### Phase 1. React·FastAPI 프로젝트 뼈대

**상태: 완료 (2026-10-26)**

FastAPI 상태 확인 API, React 연결 화면, 환경 변수 예시와 양쪽 최소 자동 테스트를 준비했습니다. 실제 데이터베이스 연결과 회원 기능은 아직 만들지 않았습니다.

#### 목표

기능이 없는 상태에서 React 화면과 FastAPI 서버를 각각 실행하고 서로 통신하게 합니다.

#### 작업

1. `backend`에 Python 가상환경과 FastAPI 프로젝트를 준비합니다.
2. 정확한 백엔드 패키지 버전을 의존성 파일에 기록합니다.
3. FastAPI 애플리케이션 시작점과 상태 확인 API를 만듭니다.
4. `frontend`에 React 프로젝트를 준비합니다.
5. 정확한 프론트엔드 패키지 버전을 잠금 파일에 기록합니다.
6. React 기본 화면에서 FastAPI 상태 확인 API를 호출합니다.
7. 개발용 CORS 허용 주소를 필요한 범위로만 설정합니다.
8. 프론트엔드 API 주소를 환경 변수에서 읽습니다.
9. `.env.example`을 프론트엔드와 백엔드에 각각 준비합니다.
10. `.gitignore`에 Python, React, SQLite3 생성 파일을 보완합니다.

#### 확인 방법

- FastAPI 상태 확인 API가 정상 응답하는지 확인합니다.
- React 개발 서버에서 기본 화면이 보이는지 확인합니다.
- React 화면이 FastAPI 응답을 받아 표시하는지 확인합니다.
- 비밀 설정과 생성 파일이 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 프론트엔드와 백엔드를 각각 실행할 수 있습니다.
- 두 프로젝트가 개발 환경에서 API로 통신합니다.
- 아직 회원이나 기록 기능은 만들지 않습니다.

### Phase 2. 데이터베이스 연결·마이그레이션·테스트 기반

#### 목표

같은 데이터 구조를 Supabase PostgreSQL과 SQLite3 테스트에서 사용할 수 있는 기반을 만듭니다.

#### 작업

1. Phase 0에서 정한 ORM과 마이그레이션 도구를 설정합니다.
2. 실제 실행에서는 환경 변수의 Supabase 연결 주소를 사용합니다.
3. 자동 테스트에서는 별도의 SQLite3 연결 주소를 사용합니다.
4. 테스트마다 깨끗한 SQLite3 데이터베이스를 만들고 정리하도록 합니다.
5. 연결 확인용 최소 데이터 구조와 첫 마이그레이션을 만듭니다.
6. 같은 마이그레이션을 PostgreSQL과 SQLite3에서 확인합니다.
7. 데이터베이스 오류를 API 오류로 안전하게 바꾸는 공통 방식을 준비합니다.
8. 실제 Supabase 연결 정보가 로그와 오류 응답에 노출되지 않게 합니다.

#### 확인 방법

- 자동 테스트가 Supabase에 접속하지 않는지 확인합니다.
- SQLite3 테스트를 반복 실행해도 이전 결과가 남지 않는지 확인합니다.
- Supabase에 마이그레이션을 적용하고 연결 확인을 할 수 있는지 확인합니다.
- 연결 실패 시 비밀 연결 주소가 화면이나 로그에 보이지 않는지 확인합니다.

#### 완료 조건

- Supabase와 SQLite3가 환경에 따라 분리됩니다.
- 동일한 모델과 마이그레이션을 두 데이터베이스에서 사용할 수 있습니다.

### Phase 3. 사용자·인증·닉네임

#### 목표

회원가입, 로그인, 닉네임 변경과 로그인 사용자 보호를 React와 FastAPI로 완성합니다.

#### 작업

1. 이메일이 중복되지 않는 사용자 데이터 구조를 만듭니다.
2. 닉네임이 중복되지 않도록 하고 2~20자 및 허용 문자 규칙을 적용합니다.
3. 비밀번호를 8~64자로 검사하고 안전하게 변환해 저장합니다.
4. 회원가입·로그인·현재 사용자 확인·닉네임 변경 API를 만듭니다.
5. 로그인 상태를 안전하게 유지하는 인증 방식을 적용합니다.
6. React 회원가입, 로그인, 계정 설정 화면을 만듭니다.
7. 가입 성공 후 로그인 화면, 로그인 성공 후 내 기록 홈으로 이동합니다.
8. 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
9. 로그인하지 않은 사용자가 개인·공개 기록 화면에 접근하지 못하게 합니다.
10. 과거 기록과 댓글은 사용자 관계를 통해 현재 닉네임을 보여주도록 준비합니다.

#### 확인 방법

- 이메일·비밀번호·닉네임의 모든 경계값을 SQLite3 자동 테스트로 확인합니다.
- 중복 이메일과 닉네임을 API와 DB 양쪽에서 막는지 확인합니다.
- 비밀번호 원문이 저장되지 않는지 확인합니다.
- 비로그인 사용자의 보호 화면 접근을 확인합니다.
- 다른 사용자의 닉네임을 바꿀 수 없는지 확인합니다.

#### 완료 조건

- `spec.md` 2장의 모든 확인 항목을 통과합니다.
- 인증 검사를 이후 API에서 공통으로 사용할 수 있습니다.

### Phase 4. 세 기록의 데이터 구조와 공통 권한

#### 목표

공부 기록, 할 일, 오류 기록이 안전하게 저장될 모델·API 규칙·소유자 검사를 준비합니다.

#### 작업

1. 공부 기록에 작성자, 제목, 내용, 공개 여부, 작성·수정 시간을 둡니다.
2. 할 일에 작성자, 제목, 완료 여부, 공개 여부, 작성·수정·완료 시간을 둡니다.
3. 오류 기록에 작성자, 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부, 작성·수정·해결 시간을 둡니다.
4. 새 기록은 기본 비공개, 새 할 일은 미완료, 새 오류는 미해결로 설정합니다.
5. API 입력과 출력 형태를 기능별로 분리합니다.
6. 작성자만 수정·삭제·상태 변경을 할 수 있는 공통 권한 검사를 만듭니다.
7. 비공개 기록은 작성자 외 사용자가 직접 주소로도 읽을 수 없게 합니다.
8. 마이그레이션과 모델 자동 테스트를 작성합니다.

#### 완료 조건

- 세 모델의 기본값, 날짜, 상태 전환 테스트가 SQLite3에서 통과합니다.
- Supabase에도 같은 마이그레이션을 적용할 수 있습니다.
- 아직 전체 사용자 화면은 만들지 않습니다.

### Phase 5. 공부 기록

#### 목표

공부 기록 작성·목록·상세·검색·수정·삭제를 API와 React 화면으로 완성합니다.

#### 작업

- 제목 1~100자, 내용 1~5,000자와 공백 규칙을 검사합니다.
- 만들기, 내 목록, 상세, 수정, 삭제 API를 만듭니다.
- 내 목록은 최근 작성 순서로 보여줍니다.
- 제목과 내용에서 내 기록을 검색하고 빈 검색어는 전체 목록으로 처리합니다.
- React 목록, 작성, 상세, 수정 화면을 연결합니다.
- 저장·수정 성공 후 목록으로 이동합니다.
- 실패하면 작성 중인 값을 유지합니다.
- 수정 시간을 상세 화면에 보여주고 삭제 전 확인창을 표시합니다.
- 작성자 외 사용자의 수정·삭제를 FastAPI에서 막습니다.

#### 완료 조건

- `spec.md` 4장의 자동 테스트와 사용자 흐름 확인을 모두 통과합니다.

### Phase 6. 할 일

#### 목표

할 일 작성·필터·완료·완료 취소·수정·삭제를 완성합니다.

#### 작업

- 제목 1~100자와 공백 규칙을 검사합니다.
- 새 할 일을 미완료·비공개로 저장합니다.
- 전체·남은 일·완료한 일 API와 화면 필터를 만듭니다.
- 미완료를 먼저, 같은 상태에서는 최근 작성 항목을 먼저 보여줍니다.
- 완료 시 완료 시간을 저장하고 취소 시 지웁니다.
- 작성자만 상태 변경·수정·삭제할 수 있게 합니다.
- 수정 시간을 목록에 보여주고 삭제 전 확인창을 표시합니다.
- 내 할 일 검색, 마감일, 중요도는 만들지 않습니다.

#### 완료 조건

- `spec.md` 5장의 자동 테스트와 사용자 흐름 확인을 모두 통과합니다.

### Phase 7. 오류 기록

#### 목표

오류 기록 작성·필터·검색·해결·미해결 전환·수정·삭제를 완성합니다.

#### 작업

- 오류 제목 1~100자, 오류 내용과 해결 방법 1~5,000자 규칙을 적용합니다.
- 미해결일 때 해결 방법을 비울 수 있게 합니다.
- 해결 상태에는 해결 방법을 필수로 하고 해결 시간을 저장합니다.
- 미해결로 되돌리면 해결 방법은 유지하고 해결 시간을 지웁니다.
- 전체·미해결·해결 필터를 만듭니다.
- 내 오류 제목과 오류 내용에서 검색합니다.
- API와 React 목록·작성·상세·수정 화면을 연결합니다.
- 수정 시간을 상세 화면에 보여주고 작성자 권한을 검사합니다.

#### 완료 조건

- `spec.md` 6장의 자동 테스트와 사용자 흐름 확인을 모두 통과합니다.

### Phase 8. 공개 기록

#### 목표

세 종류의 공개 기록을 로그인한 사용자에게 제공하면서 비공개 기록을 보호합니다.

#### 작업

- 작성자만 기록 공개 여부를 바꿀 수 있게 합니다.
- 공개 공부 기록, 할 일, 오류 기록을 모아보는 API와 React 화면을 만듭니다.
- 종류별 필터와 최근 작성 순서를 적용합니다.
- 공부 기록은 제목·내용, 할 일은 제목, 오류 기록은 제목·내용·해결 방법에서 검색합니다.
- 현재 작성자 닉네임을 보여줍니다.
- 비로그인 접근과 비공개 기록의 목록·검색·직접 주소 노출을 막습니다.
- 비공개 전환 시 댓글과 좋아요는 보존하되 다른 사용자에게 숨길 기반을 준비합니다.

#### 완료 조건

- `spec.md` 3장과 7장의 모든 확인 항목을 통과합니다.
- 두 사용자 계정으로 비공개 기록 유출이 없음을 확인합니다.

### Phase 9. 댓글

#### 목표

공개 공부 기록과 공개 오류 기록에서만 댓글을 작성·수정·삭제하게 합니다.

#### 작업

- 댓글을 공부 기록 또는 오류 기록 하나에만 연결합니다.
- 댓글 1~500자와 공백 규칙을 적용합니다.
- 오래된 댓글부터 보여줍니다.
- 댓글 작성자만 수정하고, 댓글 작성자와 기록 작성자가 삭제할 수 있게 합니다.
- 현재 닉네임을 표시합니다.
- 공개 할 일에는 댓글 API와 화면을 제공하지 않습니다.
- 비공개 전환 시 숨기고 재공개 시 다시 보여줍니다.
- 답글 기능은 만들지 않습니다.

#### 완료 조건

- `spec.md` 8장의 권한·길이·순서·공개 상태 테스트가 모두 통과합니다.

### Phase 10. 좋아요

#### 목표

공개 공부 기록과 공개 오류 기록에 한 사용자당 하나의 좋아요를 등록하고 취소하게 합니다.

#### 작업

- 사용자와 대상 기록 조합의 중복을 DB에서 막습니다.
- 처음 누르면 저장하고 다시 누르면 취소하는 API를 만듭니다.
- React에서 현재 상태와 전체 개수를 보여줍니다.
- 공개 할 일에는 좋아요 API와 화면을 제공하지 않습니다.
- 비공개 전환 시 숨기고 재공개 시 다시 보여줍니다.
- 실패하면 화면의 이전 상태와 개수를 유지합니다.

#### 완료 조건

- `spec.md` 9장의 등록·취소·중복·개수·공개 상태 테스트가 모두 통과합니다.

### Phase 11. 신고와 운영자 확인

#### 목표

공개 기록과 댓글 신고를 저장하고 운영 권한이 있는 사용자만 확인하게 합니다.

#### 작업

- 신고 대상을 공개 공부 기록, 할 일, 오류 기록 또는 댓글로 제한합니다.
- 신고 이유 1~500자와 공백 규칙을 적용합니다.
- 사용자와 신고 대상 조합의 중복을 DB에서 막습니다.
- 신고 성공·실패 API와 React 안내를 만듭니다.
- 신고만으로 대상을 자동 삭제하지 않습니다.
- 운영자 전용 신고 목록 API와 React 화면을 만듭니다.
- 일반 사용자의 신고 목록 접근을 FastAPI에서 막습니다.
- 대상이 비공개가 되어도 운영자는 신고를 계속 확인할 수 있게 합니다.
- 별도의 신고 처리 상태 기능은 만들지 않습니다.

#### 완료 조건

- `spec.md` 10장의 신고 입력·중복·자동 삭제·운영자 권한 검사를 모두 통과합니다.

### Phase 12. 반응형 UI와 공통 실패 처리

#### 목표

모든 기능을 컴퓨터와 휴대폰에서 일관되게 사용하도록 화면과 안내를 정리합니다.

#### 작업

- 밝은 배경과 카드형 목록, 공통 입력·버튼·오류 안내를 정리합니다.
- 360px 이상의 화면에서 메뉴와 콘텐츠가 겹치지 않게 합니다.
- 로딩, 빈 목록, 실패 상태를 기능별로 일관되게 보여줍니다.
- 실패 시 입력값과 기존 데이터가 유지되는지 전체 화면에서 확인합니다.
- 권한 없는 버튼을 숨기되 서버 권한 검사를 유지합니다.
- Chrome, Edge, Safari 최신 두 버전에서 주요 흐름을 확인합니다.

#### 완료 조건

- `spec.md` 11장의 반응형·브라우저 확인 항목을 모두 통과합니다.

### Phase 13. 전체 자동·통합 검사

#### 목표

SQLite3 자동 테스트와 여러 사용자 시나리오로 모든 기능이 함께 동작하는지 확인합니다.

#### 작업

1. 백엔드 전체 테스트를 깨끗한 SQLite3에서 실행합니다.
2. 프론트엔드 컴포넌트와 주요 사용자 흐름 테스트를 실행합니다.
3. 사용자 A, 사용자 B, 운영자 계정의 권한 시나리오를 확인합니다.
4. 주소와 요청값을 직접 바꿔도 권한 검사가 유지되는지 확인합니다.
5. 공개 기록에 댓글·좋아요·신고를 만든 뒤 공개 상태를 바꿔 확인합니다.
6. 닉네임 변경 후 과거 공개 기록과 댓글 표시를 확인합니다.
7. 할 일과 오류의 상태 전환 및 날짜 변화를 확인합니다.
8. `spec.md`의 모든 확인 항목을 처음부터 끝까지 점검합니다.
9. 첫 버전 제외 기능이 추가되지 않았는지 확인합니다.

#### 완료 조건

- 프론트엔드와 백엔드 전체 자동 테스트가 통과합니다.
- 권한 없는 접근과 비공개 정보 노출이 없습니다.
- SQLite3 테스트가 Supabase 실제 데이터를 사용하거나 변경하지 않습니다.

### Phase 14. Supabase 최종 연결과 배포 준비

#### 목표

실제 Supabase 데이터베이스와 온라인 환경에서 첫 버전의 핵심 흐름을 확인하고 실행 문서를 완성합니다.

#### 작업

1. Supabase 프로젝트의 실제 연결 주소를 배포 환경 변수에 설정합니다.
2. 데이터베이스 마이그레이션을 Supabase에 적용합니다.
3. 실제 서비스용 인증 비밀값과 허용 주소를 설정합니다.
4. FastAPI 백엔드와 React 프론트엔드를 온라인 환경에 연결합니다.
5. 운영자 계정을 준비하고 신고 화면 권한을 확인합니다.
6. 회원가입부터 신고까지 핵심 흐름을 실제 환경에서 점검합니다.
7. 서로 다른 컴퓨터 또는 휴대폰에서 같은 계정의 데이터가 보이는지 확인합니다.
8. 데이터베이스 변경, 실행, 테스트, 배포, 문제 복구 방법을 `docs/setup.md`에 기록합니다.
9. `.env.example`에 필요한 이름만 있고 실제 비밀값은 없는지 확인합니다.

- [ ] 회원가입, 로그인, 닉네임 변경이 동작합니다.
- [ ] 세 기록의 작성·조회·수정·삭제와 상태 변경이 동작합니다.
- [ ] 비공개 기록은 작성자 외 사용자에게 노출되지 않습니다.
- [ ] 공개 기록의 종류별 필터와 검색이 동작합니다.
- [ ] 댓글, 좋아요, 신고의 대상과 권한 규칙이 맞습니다.
- [ ] 운영자만 신고 목록과 내용을 볼 수 있습니다.
- [ ] 360px 이상 화면과 지원 브라우저에서 주요 기능을 사용할 수 있습니다.
- [ ] SQLite3 전체 테스트가 통과합니다.
- [ ] Supabase에서 핵심 사용자 흐름이 동작합니다.
- [ ] 다른 컴퓨터에서도 같은 사용자 데이터를 볼 수 있습니다.
- [ ] 범위 밖 기능이 추가되지 않았습니다.

#### 완료 조건

- `spec.md`의 모든 기능이 실제 온라인 환경에서 동작합니다.

## 7. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 확인 결과와 확정한 기술 구성을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
